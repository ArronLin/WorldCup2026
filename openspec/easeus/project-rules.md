# 项目规范

## 适用范围与依据

本规范约束 WorldCup2026 的长期工程原则、架构边界、兼容要求和修订方式。具体功能需求与验收场景在 OpenSpec 变更及能力规范中维护。

工程规则以本次适配启用的 effective_rules/effective_policy 为依据。知识库与源码用于核实现状，已确认需求用于定义期望；发现差异时记录来源、适用版本与判断依据。存量缺陷、待查事实和单次功能需求不自动成为长期规范。

## 架构边界

以原生 HTML/CSS/JavaScript 和 ES Modules 为技术基线，保持应用入口、路由视图、独立特性、共享逻辑和静态资源的职责分离。入口负责组合与初始化，视图负责页面呈现，特性逻辑在对应模块中维护。

浏览器与 Function 共用的数据归一化和查询语义在共享层维护；共享逻辑保持两侧运行环境兼容，避免各自复制后产生口径差异。

核心赛事浏览保持独立于外部 AI 服务。AI 界面与服务端处理边界清晰，AI 配置缺失或服务不可用时，不阻断核心静态赛事浏览。

依据：README.md 的技术与架构、项目结构说明，证据 E-0a16cd0daf594d86。

## 数据与兼容约束

赛事数据以 public/data/ 的静态 JSON 快照为基线来源。数据更新应保持标识符、跨文件引用、数据结构与中英文词典的一致性，并通过项目数据契约校验。

浏览器赛事数据读取复用统一数据层及其缓存机制。调整数据接口、缓存或错误处理时，应评估现有调用方的返回结构与行为兼容性，不将既有降级表现或缺陷直接定义为新的期望。

保持现有 Hash 深链接、页面按需加载及中英文界面的兼容性。改变路由、数据来源或共享接口时，在对应变更中说明迁移影响和验证方式。

依据：README.md、package.json 与 src/store.js，证据 E-0a16cd0daf594d86、E-8d9f52a0905e4dc2、E-aeeedd018ffe43b2。

## 运行与交付兼容

当前开发工具链以 Node.js 24 及以上、ES Modules 为兼容基线。依赖及工具链调整须评估开发、测试、构建和部署之间的兼容影响，并同步维护依赖声明与锁文件。

保持构建前的数据校验环节。静态发布产物与 Netlify Functions 分别承担前端交付和服务端处理，函数运行所需的数据资源应随部署提供。改变输出目录、函数目录或资源打包方式时，同步调整相关配置与说明。

依据：README.md、package.json、vite.config.js 和 netlify.toml，证据 E-0a16cd0daf594d86、E-8d9f52a0905e4dc2、E-eead9f180ce64d8e、E-bfe85bb5eac14818。

## 生产范围与报告证据

采用 src/**/*.js 和 netlify/functions/**/*.mjs 作为自有生产代码的默认范围，按功能确认新增生产路径及排除项，记录明确基线和排除理由。覆盖率配置中的采集范围不直接等同于某个功能已确认的统计范围。

每个功能提供新增自有生产代码单元测试行覆盖率 HTML 报告，以及需求与 TDD 证据 HTML 报告。报告使用通用契约关联需求、测试源码、真实执行结果、覆盖率和实际 Red/Green 证据；报告核心不绑定语言、测试框架或包管理器。

采集能力缺口纳入对应变更的计划与 tasks，明确生产范围、测试源码清单、真实套件分类、受支持的结果与覆盖率格式、功能基线及证据关联。现有工具可作为适配来源，不直接沿用历史功能或其他框架的报告入口。

缺失、失败、跳过、未执行或不适用的状态应如实展示，不能以已有脚本或报告文件的存在推定完成。单元覆盖率的统计口径和门槛遵循上方启用规则。

范围依据：用户已确认的 production_scope 答案及 vite.config.js，证据 E-eead9f180ce64d8e。报告要求依据本次 effective_policy.reports 与 reporting 通用契约。

## 修订机制

修订应说明原因、依据、受影响章节、兼容影响和迁移安排，由用户评审后确定。架构或工具链发生经确认的变化时，同步更新本规范和相关工程配置，避免文档与实现长期分离。

受管工程规则区段随有效规则快照更新，保持完整且仅出现一次。其他来源的同名政策不自动覆盖本次有效规则；未启用要求不形成隐含门槛。

修订记录关联可追溯的变更与证据。具体缺陷和功能任务在相应变更中处理，只有经确认具有长期适用性的原则才纳入本规范。
