# 缺陷评估：赛程日期缺少弹出日历选择

## 评审摘要

- **结论**：问题成立，属于当前用户明确提出的可用性改进。现有实现符合此前文本输入方案，但无法满足本次“不必手写、直接通过弹出日历选择”的期望；没有证据表明日期过滤算法错误。
- **影响**：开始、结束日期均需手动输入格式，增加操作成本和输入错误机会；仍可通过手写完成筛选，无数据损坏或核心浏览中断，严重程度为中。
- **复现状态**：已在当前应用的 Chromium 151.0.7922.34 中点击日期输入，核对真实 DOM 与生产事件代码，确认两项均为文本框，表单只有应用、清除按钮，没有日历入口或弹层实现。
- **建议**：增加可通过鼠标和键盘打开的日期弹层，以点选完成主要流程；保留文本输入作为兼容入口，选日期只更新草稿，点击“应用日期”才筛选。
- **待确认项**：没有阻塞本次诊断的问题。用户已确认需要日历选择；保留手写兼容入口、弹层初始月份和导航细节属于下述推荐方案，尚非已批准视觉稿。若后续要求完全禁止手写，需同步调整原非法草稿验收。
- **主要风险**：直接替换现有输入类型可能影响原文保留；日历焦点、语言重绘和窄屏布局需补充验证。

## 用户报告

> 上个功能实现的日期过滤，需要用户手动填写，既不方便也容易出错。应该直接以日历的方式弹出，让用户直接选择

## 现象与复现

1. 打开当前 WorldCup2026 应用并进入 `#/schedule`，等待赛程加载完成。
2. 点击“开始日期”，再检查“结束日期”的输入方式。
3. 当前两项均为 `type="text"`，只能输入日期文字；表单按钮为“应用日期”“清除日期”，没有日历选择操作。
4. 期望：用户打开对应日期的日历，点选年月日即可形成日期草稿，不必手工组织 `YYYY-MM-DD` 字符串。

本轮使用既有本地开发服务，以独立 Playwright/Chromium 会话操作当前源应用；未使用项目 E2E 配置，未重建产物或重跑全量测试。DOM 检查与源码相互印证；未生成截图，也未将拟议日历标为已实现或已验证。

## 建议修复方案

**首选：保留原文本草稿，增加特性内的可访问日历弹层。** 开始、结束日期各有明确命名的选择入口；点击日期区域或入口打开对应弹层。使用现有按钮、图标及主题变量，不新增整页月历，不引入网络请求或日期持久化。

建议的可观察边界：

- 选择有效日期后，以四位年份的 `YYYY-MM-DD` 写入对应草稿并关闭弹层，焦点返回对应入口；另一端不变，列表、数量和生效摘要在主动应用前保持原值。
- 初始月份优先采用对应字段的有效草稿，其次有效生效值，再取快照最早比赛日；仅作为导航起点，不限制赛事范围外日期。提供月份切换及年份／月份快速定位，避免跨多年逐月点击。
- 不存在的日期不可选择；允许同日、单端和空端点，倒置区间仍由现有应用校验处理，不自动交换。单端清空只修改该端草稿；原“清除日期”保持一次清除全部日期影响的行为。
- 点击外部或按 Escape 取消选择，不改草稿／生效值；键盘可到达入口、导航和日期，关闭后恢复焦点。显式处理弹层打开期间语言切换、页面离开、重渲染和目标失效，不能让弹层或焦点遗留在旧 DOM。
- 月份、按钮和日期可访问名称成对维护中英文；以年月日数值计算日历，不通过时间戳转换比赛日。保留 `0001`—`9999` 边界、闰年及跨时区一致性。

**备选**：在文本字段旁使用独立原生日期选择入口，将合法选择写回文本草稿，减少自绘日历代码。需先验证目标浏览器的弹出能力、键盘操作、关闭行为及自动化可测性；不能以仅调用选择器接口成功代替真实可见、可选择的验证。单纯将现有字段改为 `type="date"` 会改变非法草稿语义，不作为兼容修复首选。
