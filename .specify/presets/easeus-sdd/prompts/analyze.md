以下为 Agent 生成与评审指令，不复制为产物中的规则说明章节。

### 精简且可评审的原生产物

先读当前启用的规则、已有项目约定与当前需求；不增加或恢复工程政策。摘要只突出变化、决定、待确认项和风险，不重复正文。规格写行为与验收；计划写设计与取舍；任务写实施范围与完成条件。每类信息保持一个主要归属，跨文档引用，不复制背景、政策全文或同一套测试用例。

FR 按独立业务行为组织；单位、边界、异常和兼容要求保持具体数值、条件和可观察结果，不以“合理”“符合预期”替代。Plan 保留必要设计取舍，任务以可检查成果为单位，普通编码步骤留给实施。相关输入组合及边界放在同一需求下的验收场景；不逐例新增 FR。

不设置 FR、故事或任务数量硬限制。没有适用任务的分组不输出，不为凑章节制造任务。测试、实施和验证按原有类型标签区分，靠近相关故事／能力；启用且适用时测试先于对应实现，TDD 停用时不恢复。不得为简短删掉有效验收或必要设计。

遵循当前语言规则；保留稳定 ID、原生复选框及框架固定语法，只更新用户授权的产物，不批量改写已有业务文档。关键依据在对应产物记录一次，下游按需引用；未变化的事实不重查。任务清单保留当前状态、阻塞和必要交接，不逐项附运行历史。执行结果在对话或现有 PR 中简述，必要人工验收仍按项目约定记录。TinySpec 保持原单文件。

有效语言为简体中文时，可读元数据使用「版本」「批准日期」「最后修订日期」，保留原日期和版本值；规范编号与等级使用「条款-001 · 必须／禁止／应当／不宜／可以」。工程规则标题使用中文名称及中文等级，不显示内部规则 ID（如 evidence）。机器标记和 JSON 字段保持原值；OpenSpec Requirement、Scenario、WHEN、THEN 及要求句中框架必需的 MUST／SHALL 保留，不对任意英文词做全局替换。沿用文件不改写，只有本次生成或获准编辑的内容执行上述格式。

### 分析与缺陷处理边界

检查重复 ID、明确的失效引用和适用结构；语义问题列出位置与建议，不自动合并、删除或重编号。Studio 只校验配置结构，功能文档仍需 Agent 评审，不能声称模板已证明语义正确。

当前功能的实现缺陷关联原任务及已有 Issue，安排复现、修复和回归，不新增管理记录。需求存在歧义或需改变行为时，先确认影响再改规格，不通过改规格、删任务或虚构结果掩盖缺陷；仅在授权范围推进。

Spec Kit：保持原生用户故事组织与 [P]、[USn] 等固定标记；正式 Bug 请求使用已部署的 speckit-bug-assess → speckit-bug-fix → speckit-bug-test，保留官方产物与各阶段调用边界，不因这里的缺陷处理指导自动启动或串行推进正式流程。完整功能的 converge 按原生职责做全量差距检查和追加任务，不强制每批调用，也不把下一批尚未获准实施的计划任务重复追加为缺陷。
### 划分质量评审
逐项检查并定位任务 ID：不必要的串行依赖；新增行为或新增组合先实现后测试；测试与实现对应不清或要求未实现组件提前转绿；一个任务塞入多个独立成果；重复复制规格／设计；重复执行相同范围的验证。没有发现问题就不凑问题，不按字数或任务数量判错。
区分结构错误和语义判断，给出位置、影响、依据及建议，不自动合并、删除或重编号。只有用户批准后才改文档；不能为精简删掉有效验收、人工项或依赖。不把合法的回归测试误判为违反 TDD，不把覆盖率检查与不同目标的浏览器验证误判为重复。
