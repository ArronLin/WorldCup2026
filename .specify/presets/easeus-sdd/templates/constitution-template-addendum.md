### 精简且可评审的原生产物

先读当前启用的规则、已有项目约定与当前需求；本指导不增加或恢复工程政策。摘要只突出目标、本次变化、关键决定、待确认项和主要风险，不重复正文，没有内容的可选项不凑数。规格写行为与验收；计划写设计与取舍；任务写实施范围与完成条件。为各类信息保持一个主要归属，跨文档引用已有定义，不复制背景、政策全文或同一套测试用例。

FR 按独立业务行为组织。单位、边界、异常和兼容要求可集中成紧凑表格，保持具体数值、条件和可观察结果；不能用“合理”“符合预期”代替明确要求。Plan 保留有必要提前决定的架构、接口、安全、兼容和迁移细节，普通编码步骤留给实施。任务以可检查的工程成果为单位，写明稳定 ID、文件或组件范围、必要依赖和完成条件；测试与验证写明行为、断言和实际入口，避免拆成“打开文件”“添加一行”等零碎任务，也不能把多个独立成果塞进一个无法判断完成的任务。

不设置 FR、故事或任务数量硬限制。按当前功能实际范围生成必要章节；没有适用任务的分组不输出，不为满足模板而制造测试、实现或验证任务。测试、实施和验证使用不同类型标签，保持靠近相关故事或能力；启用 TDD 时测试先于对应实现并实际执行，TDD 停用时不恢复。小改动可紧凑表达，复杂功能保留边界和异常，不用字数目标删掉验收条件。

所有面向人的标题、表头与说明遵循当前语言规则。保留稳定 ID、原生复选框及框架固定语法；只更新用户授权的产物，已有任务 ID、人工记录与历史验证不批量改写。来源细节后置，不粘贴原始日志，不新增阶段报告文件、重复测试汇总表或证据包；阶段结果在对话中简述。TinySpec 保持原单文件。

### 分析与缺陷处理边界

分析时检查重复 ID、明确的失效引用、当前框架及场景必需的结构，再检查重复表达、任务过细或过大。语义问题列出具体位置、影响和修改建议，不自动合并、删除或重编号。Studio 只校验生成配置的结构；功能文档仍需 Agent 结合上下文评审，不能声称模板已证明语义正确。

发现已明确预期的当前功能实现缺陷时，关联原任务及已有 Issue，按当前启用规则安排复现测试、修复和回归；不默认新增独立缺陷文档或管理记录。需求存在歧义或确需改变行为时，先说明影响并确认，再更新相关规格；不得通过改规格、删任务或虚构测试结果掩盖缺陷。修复和测试仅在已授权范围推进，环境问题如实区分，不伪装成有效失败测试。

Spec Kit：保持原生用户故事组织与 [P]、[USn] 等固定标记；正式 Bug 请求使用已部署的 speckit-bug-assess → speckit-bug-fix → speckit-bug-test，保留官方产物与各阶段调用边界，不因这里的缺陷处理指导自动启动或串行推进正式流程。完整功能的 converge 按原生职责做全量差距检查和追加任务，不强制每批调用，也不把下一批尚未获准实施的计划任务重复追加为缺陷。

### 混合任务与人工交接

先读项目已有验收、审批和发布约定（包括宪法及其引用），再核对当前规格的验收场景。默认不新增最终人工验收任务。仅为项目约定或已明确的功能需求生成必要人工测试、评审或验收；现有人工任务已覆盖要求时不重复增加。负责人或发布影响不清楚时走原有澄清流程。当前机器缺少设备、数据或权限但其他环境能自动运行的任务仍归自动化测试，用“阻塞原因”说明当前限制。不要把失败或缺失实现转成人工任务。不降低启用规则和既有门槛；停用规则保持停用。

启用简体中文规则时，所有本次生成或更新的 Markdown（含规格、计划、研究、数据模型、契约、快速验证、检查清单和任务交接）在交付前检查标题、表头、字段名、类别、状态和说明，全部采用简体中文。命令、路径、代码标识符、框架要求的固定语法和验收所需的原文文案照实保留。不要把英文工具输出、模板标签或内部字段名当作评审正文。

需要混合任务或显式依赖时，在原任务文档写入 `<!-- repo-sdd:hybrid-tasks:v1 -->`，保留复选框、任务 ID、[P]、[USn] 等。中文清单的人工项用 `[人工]`；无执行者标签时沿用 Agent 执行。“类型”可填开发、自动化测试、人工测试、评审、验收或其他。用缩进说明行写 `依赖：T010, T011`；人工项写“负责人”“环境”“原因”“步骤”“预期”“证据”和“发布必需：是”或“发布必需：否”。默认阻塞发布。确需正式签收时才写“最终验收：是”。没有人工任务时不输出空分组。明确停用时使用 `<!-- repo-sdd:hybrid-tasks:v1 {"enabled":false} -->` 并执行原生规则。

非中文清单可使用既有英文约定：[MANUAL]、Type（DEVELOPMENT / AUTOMATED_TEST / MANUAL_TEST / REVIEW / ACCEPTANCE / OTHER）、Dependencies、Owner、Environment、Reason、Steps、Expected、Evidence、Required for release、Final acceptance、Blocked reason、Related to、Tester、Execution date、Result、Result evidence、Actual environment、Issue、Reproduction、Deferred by、Deferred until、Deferral reason、Implementation review、Reviewed revision。布尔值使用 true / false，结果使用 passed / failed。已有英文任务仍可读取；中文清单不重复写英文别名。

### 批次范围与状态检查

执行前读取整份清单并说明本轮范围。未指定批次时沿用当前授权范围，内部按依赖分批实施和验证，不默认增加逐批人工审批；明确要求只执行某批时，完成后停止，不提前执行未授权批次。原生任务文件是唯一任务清单，不新增批次状态文件。

运行当前框架 `workflow/run.ps1 inspect-tasks --tasks <仓库相对路径>`，或使用同目录 `python -B runtime.py inspect-tasks --project . --rules <当前规则快照> --tasks <仓库相对路径>`。运行组件路径见当前框架的项目指南和规则目录。可用 `--story US1`、`--phase <标题>`、`--task-id <ID>`（可重复）限制批次。无选择参数检查整份清单；重复任务 ID 取并集，不同参数之间取交集。父级阶段包含子章节；同名阶段按候选位置用明确任务 ID 消歧。依赖始终检查整份清单，范围外前置任务未完成即阻塞，不自动扩大范围。空匹配、未知 ID、重复 ID、非法或循环依赖必须先处理，不能回退为执行所有任务。

无混合任务标记的旧清单也尊重显式范围，保持原生复选框语义；不得仅凭自由文本或未启用的扩展标记赋予人工任务或延期审批语义。先读已有交接约定，发现必须人工执行但标记不清楚时澄清，不自行跳过。

检查 JSON 的 `result_version: 2`，按 `selected_tasks` 核对范围，并读取 `batch_remaining_ai`、`batch_pending_manual`、`ready_ai` 和 `blocked`（包含阻塞原因）。`batch_status` 为 invalid 时修正输入；ready 时仅执行获准的 ready_ai；blocked 时说明前置缺口，不能称为完成；pending_manual 时说明 AI 已完成、仍待人工；complete 仅表示所选任务记录全部完成。每完成 AI 任务，按原生格式更新复选框并重算，保持人工复选框原样。无关人工项不妨碍独立 AI 工作。

`batch_ai_complete` 只表示范围内 AI 任务完成；`execution_batch_complete` 表示范围内所有任务完成且没有结构或依赖问题，不能再用“暂无可执行任务”替代。全局 `implementation_complete`、`pending_manual` 和功能状态仍按整份清单计算。退出码为 0 仅表示检查成功，不代表任务完成；`verification: unverified` 不得被任务勾选、Agent 声明或批次 complete 改写为测试、覆盖率或 CI 通过。检查器不形成权限沙箱或审批系统，执行仍受用户授权限制。

批次结束在对话中列出范围、已完成和剩余 AI 任务数、待人工验收项、被阻塞任务及原因、实际自动化测试结果、可交接范围和下一步，不默认新增报告文件。区分当前批次暂无可执行任务和整份清单的 AI 任务已完成。人工通过后由授权人员填写“执行人”“执行日期”（YYYY-MM-DD）“实际环境”“结果：通过”和“结果证据”，然后勾选。失败保持未勾选，记录“结果：失败”“问题编号”“复现步骤”和证据，修复项用“关联任务”引用人工任务 ID，修复后重新验证。Agent 不写入人工结果或勾选，也不删除未通过项。延期需按现有流程批准，记录“发布必需：否”“延期批准人”“延期截止日期”“延期原因”，保留待验收状态。

最终核对时先按原生流程检查实现差距和真实测试，再在适当的已完成任务记录“实施复核：通过”和“复核修订”（填 inspect-tasks 返回的 revision）。只有完成实际核对才记录，正式人工验收项的结果和复核修订由授权人员填写。没有人工验收要求时，可以在现有 AI 验证任务内记录复核。当前修订的任务和验收记录齐备后报告“已收尾”，测试、CI 与审批真实性由项目原有机制核验。只读询问不得改文件；续做先核对剩余任务。需求变更使结果失效时，保留历史并重新打开受影响项。

Spec Kit：已启用混合任务的文档在 implement 中按当前可执行 AI 项推进；原生全量完成条件仍用于最终交付。plan/tasks 分开本地验证和人工交接；analyze 不把已明确交接的测试当作任务遗漏。checklist 仍用于需求质量，不把人工执行用例搬进需求质量检查清单；原有检查清单门禁保持。完整功能的 converge 继续全量核对实现差距并按原生规则追加任务，不强制每批调用；人工任务未完成时报告“待人工验收”；仍有被阻塞的实现则列明，不能给出全量收敛结论。TinySpec 在原单文件内使用同一交接方式，done 只表示开发实施已完成，另明确待人工验收。官方 Bug 沿用 assessment.md、fix.md、test.md；未执行用例不得写为 Result: Passed，不自动推进下一阶段。
