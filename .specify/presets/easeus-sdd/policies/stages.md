以下为 Agent 生成与评审指令，不复制为产物中的规则说明章节。

### 精简且可评审的原生产物

先读当前启用的规则、已有项目约定与当前需求；本指导不增加或恢复工程政策。摘要只突出目标、本次变化、关键决定、待确认项和主要风险，不重复正文，没有内容的可选项不凑数。规格写行为与验收；计划写设计与取舍；任务写实施范围与完成条件。为各类信息保持一个主要归属，跨文档引用已有定义，不复制背景、政策全文或同一套测试用例。

FR 按独立业务行为组织。单位、边界、异常和兼容要求可集中成紧凑表格，保持具体数值、条件和可观察结果；不能用“合理”“符合预期”代替明确要求。Plan 保留有必要提前决定的架构、接口、安全、兼容和迁移细节，普通编码步骤留给实施。任务以可检查的工程成果为单位，写明稳定 ID、文件或组件范围、必要依赖和完成条件；测试与验证写明行为、断言和实际入口，避免拆成“打开文件”“添加一行”等零碎任务，也不能把多个独立成果塞进一个无法判断完成的任务。

不设置 FR、故事或任务数量硬限制。按当前功能实际范围生成必要章节；没有适用任务的分组不输出，不为满足模板而制造测试、实现或验证任务。测试、实施和验证使用不同类型标签，保持靠近相关故事或能力；启用 TDD 时测试先于对应实现并实际执行，TDD 停用时不恢复。小改动可紧凑表达，复杂功能保留边界和异常，不用字数目标删掉验收条件。

所有面向人的标题、表头与说明遵循当前语言规则。保留稳定 ID、原生复选框及框架固定语法；只更新用户授权的产物，已有任务 ID、人工记录与历史验证不批量改写。来源细节后置，不粘贴原始日志，不新增阶段报告文件、重复测试汇总表或证据包；阶段结果在对话中简述。TinySpec 保持原单文件。

### 分析与缺陷处理边界

分析时检查重复 ID、明确的失效引用、当前框架及场景必需的结构，再检查重复表达、任务过细或过大。语义问题列出具体位置、影响和修改建议，不自动合并、删除或重编号。Studio 只校验生成配置的结构；功能文档仍需 Agent 结合上下文评审，不能声称模板已证明语义正确。

发现已明确预期的当前功能实现缺陷时，关联原任务及已有 Issue，按当前启用规则安排复现测试、修复和回归；不默认新增独立缺陷文档或管理记录。需求存在歧义或确需改变行为时，先说明影响并确认，再更新相关规格；不得通过改规格、删任务或虚构测试结果掩盖缺陷。修复和测试仅在已授权范围推进，环境问题如实区分，不伪装成有效失败测试。

Spec Kit：保持原生用户故事组织与 [P]、[USn] 等固定标记；正式 Bug 请求使用已部署的 speckit-bug-assess → speckit-bug-fix → speckit-bug-test，保留官方产物与各阶段调用边界，不因这里的缺陷处理指导自动启动或串行推进正式流程。完整功能的 converge 按原生职责做全量差距检查和追加任务，不强制每批调用，也不把下一批尚未获准实施的计划任务重复追加为缺陷。
