### 交互与产物语言
面向团队评审的自然语言使用简体中文，包括标题、小标题、表头、任务类别和状态说明；命令、路径、代码标识符及框架固定标记保持原样。必要术语首次出现时提供简短解释，后续不重复翻译；遵守项目已有的公共 API、国际化和文档约定，不照抄基础模板英文标题作为最终自然语言标题。

### 真实 TDD
新增或修改可单测行为及修复缺陷时，先编写测试并实际运行，确认测试因预期行为尚未实现而失败，再编写最小实现使测试通过，随后按需重构并回归验证。依赖、环境或语法错误不能作为有效的 Red；不得将事后补写测试宣称为 TDD。纯重构先确认已有测试通过，再重构并回归，不人为制造失败；遗留代码可先补描述现状的特征测试。缺陷无法稳定复现时先调查并说明限制，不编造失败；探索性原型、环境配置及纯视觉调整采用适用验证。不适用或无法可靠执行测试先行时说明原因及替代验证，不得宣称为 TDD。

### 可计量新增业务逻辑测试覆盖率
对本次新增或修改、可可靠采集的自有可执行业务逻辑，按项目明确的单元测试覆盖率指标和变更范围检查，默认门槛为 80%。计划中明确采用行、语句或分支覆盖率及计算范围，不混用指标，不以全项目覆盖率代替变更范围指标；关键行为、边界和错误路径不能因达标而省略测试。纯声明式 UI、生成代码、资源和配置可排除百分比分母，说明理由并采用适用的行为验证；不按文件类型整包排除，QML 内可执行 JavaScript 业务逻辑仍须单独评估，复杂逻辑优先移入可单测模块。无可靠采集能力记为未核验／能力缺口，不视为不适用，不得填成 0% 或 100%；qmlprofiler 等性能分析事件不能作为覆盖率证明。

### 有效测试与验证
测试必须调用真实被测生产逻辑，包含能识别错误行为的断言，并实际被发现和执行。禁止占位成功、恒真断言、替换被测核心逻辑与静默跳过；允许合理使用测试替身隔离网络、时钟、数据库、文件系统等外部依赖，并按风险补充集成验证。未实际执行或失败的测试不得宣称通过。对高风险或断言有效性存疑的逻辑，按需采用可恢复的反向验证或变异测试，不要求每次修改都执行。

### 来源与事实核实
知识库与源码说明现状，已确认需求定义期望；仅对影响需求、设计或兼容性判断的关键结论，在对应原生产物中简短记录必要来源与适用版本，不重复复制源码、知识库内容或工程规则全文。未知明确说明，现状缺陷不得自动固化为规范；知识库与当前源码不一致时指出差异，不仅凭更新时间推断谁正确。
遵守用户的阶段授权和读写边界；只把实际执行的工作标为完成；未运行测试不得宣称通过。所有面向人工评审的 SDD 文档采用摘要先行、需确认项集中、正文分层、细节后置的结构；不复制背景，不粘贴原始日志。开发产物以框架文档、代码、测试和必要任务状态为主；不默认生成 evidence、过程收据、源码副本、逐任务说明或 HTML 报告。UI 任务仅按已确认的验证方案保留必要界面证据，非 UI 任务不增加截图要求。实际命令与结果在对话中简述，覆盖率和质量门槛沿用仓库已有工具与 CI。覆盖率百分比只约束工具可可靠计量的可执行业务逻辑；纯声明式 UI（包括 QML）等不可可靠计量内容采用适用的自动化行为测试，性能分析事件不能作为覆盖率证明。



工程规则约束 Agent 行为，不要求在每份产物重复展示。spec 只保留需求与验收；plan 按需记录宪法检查、测试策略和覆盖率适用性；tasks 记录实际测试、实施与验证任务；检查清单只记录需评审的问题。不复制工程规则全文，不新增“阶段规则与依据”章节。

### 精简且可评审的原生产物

先读当前启用的规则、已有项目约定与当前需求；本指导不增加或恢复工程政策。摘要只突出目标、本次变化、关键决定、待确认项和主要风险，不重复正文，没有内容的可选项不凑数。规格写行为与验收；计划写设计与取舍；任务写实施范围与完成条件。为各类信息保持一个主要归属，跨文档引用已有定义，不复制背景、政策全文或同一套测试用例。

FR 按独立业务行为组织。单位、边界、异常和兼容要求可集中成紧凑表格，保持具体数值、条件和可观察结果；不能用“合理”“符合预期”代替明确要求。Plan 保留有必要提前决定的架构、接口、安全、兼容和迁移细节，普通编码步骤留给实施。任务以可检查的工程成果为单位，写明稳定 ID、文件或组件范围、必要依赖和完成条件；测试与验证写明行为、断言和实际入口，避免拆成“打开文件”“添加一行”等零碎任务，也不能把多个独立成果塞进一个无法判断完成的任务。

不设置 FR、故事或任务数量硬限制。按当前功能实际范围生成必要章节；没有适用任务的分组不输出，不为满足模板而制造测试、实现或验证任务。测试、实施和验证使用不同类型标签，保持靠近相关故事或能力；启用 TDD 时测试先于对应实现并实际执行，TDD 停用时不恢复。小改动可紧凑表达，复杂功能保留边界和异常，不用字数目标删掉验收条件。

所有面向人的标题、表头与说明遵循当前语言规则。保留稳定 ID、原生复选框及框架固定语法；只更新用户授权的产物，已有任务 ID、人工记录与历史验证不批量改写。来源细节后置，不粘贴原始日志，不新增阶段报告文件、重复测试汇总表或证据包；阶段结果在对话中简述。TinySpec 保持原单文件。

### 分析与缺陷处理边界

分析时检查重复 ID、明确的失效引用、当前框架及场景必需的结构，再检查重复表达、任务过细或过大。语义问题列出具体位置、影响和修改建议，不自动合并、删除或重编号。Studio 只校验生成配置的结构；功能文档仍需 Agent 结合上下文评审，不能声称模板已证明语义正确。

发现已明确预期的当前功能实现缺陷时，关联原任务及已有 Issue，按当前启用规则安排复现测试、修复和回归；不默认新增独立缺陷文档或管理记录。需求存在歧义或确需改变行为时，先说明影响并确认，再更新相关规格；不得通过改规格、删任务或虚构测试结果掩盖缺陷。修复和测试仅在已授权范围推进，环境问题如实区分，不伪装成有效失败测试。

Spec Kit：保持原生用户故事组织与 [P]、[USn] 等固定标记；正式 Bug 请求使用已部署的 speckit-bug-assess → speckit-bug-fix → speckit-bug-test，保留官方产物与各阶段调用边界，不因这里的缺陷处理指导自动启动或串行推进正式流程。完整功能的 converge 按原生职责做全量差距检查和追加任务，不强制每批调用，也不把下一批尚未获准实施的计划任务重复追加为缺陷。
