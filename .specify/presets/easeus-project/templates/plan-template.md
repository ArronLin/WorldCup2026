## 本地验证与覆盖率口径

| 验证层级 | 现有入口与本次需明确的内容 |
| --- | --- |
| 纯逻辑与契约 | `npm test -- <实际测试文件>`；文件位于 `tests/**/*.test.js`，写明真实生产入口、行为及关键断言。 |

| Function 联调 | README 入口为 `npx netlify-cli dev`，执行前核实所需配置及权限；`npm run dev` 不包含生产 Function。 |
| 单元覆盖率 | `npm run test:coverage`；变更比较入口为 `npm run coverage:added -- --baseline <本次适用基线> --output <既有约定输出位置>`，实际参数和基线可用性执行前核实。 |

## UI 方案增补（仅 UI 需求）

沿用规格的 UI 分类、模式、设计输入和基线；非 UI 不生成本节，待确认先澄清。仅执行获准阶段，规划不自动运行应用或实施。

在现有变更地图中填写“需求／验收 ID → 设计章节或节点 → 页面和选择器／模块 → 复用或新增 → 状态与事件 → 样式来源 → 验证方式”。新增组件说明现有实现不能满足的原因。

视觉基础核对 `tokens.css`：暗色默认及亮色主题、主强调色 `#00D9A3`、辅助色 `#0EA5E9`／`#7C3AED`、Inter 与中文系统回退、4／8／16／24／40／64px 间距、8／14／20px 圆角；布局核对 `base.css`、`pages.css`，聊天核对 `chat.css`。这些只作为源码复用依据，具体设计以本次已确认需求为准。

### UI Gate 1：编码前设计确认

在原计划或验收位置记录设计材料可读且足够、基线及主要验收明确、组件映射和验证方式可行、必要人工确认已获得。影响实现的缺口未解决时暂停 UI 实施并说明待补项；同一已确认且未变化内容不重复批准。该 Gate 是 Agent 检查约定，不是框架审批引擎。

### UI Gate 2：初步 UI 验证方案

完整模式按依赖安排结构及主要控件、实际运行与截图、基线对照、重要偏差修正、剩余业务逻辑、交互及适用视觉回归。为首轮运行准备最小必要数据，模拟状态注明，不能替代最终集成验证；轻量模式局部修改后完成对应验证。

明确浏览器及版本、系统、视口、缩放或 DPI、主题、字体环境、页面与状态、候选版本及未提交范围、验证者。实际截图沿用项目约定目录；目录未知先核实，不强制建立证据包。环境不可比先校准。实际运行证据不能由设计图、旧截图或构建成功替代；无运行或看图能力时等待人工或适用工具，不宣称通过。

在已有验收位置按需记录简短差异表：验收 ID、预期、实际、证据引用、类别、严重程度（阻断／重要／轻微）、修复建议。检查布局、组件、颜色、字体、尺寸、间距及状态；交互以实际操作或行为测试验证，静态图及像素相似度不能独立证明通过。完整模式继续剩余业务开发前处理重要偏差。

设计变更或偏差先判原因：需求缺失或冲突先澄清；方案不适用修订方案和任务；实现偏离仅修正相关实现；设计变化重新确认受影响基线。保留有效任务 ID 和技术决定，只重开受影响任务，重新核验失效截图与结论，不重新生成整个功能，不反改正确需求迁就实现。文档修订不自动授权实施。
