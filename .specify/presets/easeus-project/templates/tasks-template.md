## EaseUS：tasks 阶段规则与依据
使用当前规则快照和已评审项目约定；为适用规则记录落实方式及完成条件。

### 交互与产物语言
所有面向人的自然语言内容，包括标题、小标题、表头、任务类别、状态说明、目标、依赖与验证文字，使用简体中文；命令、文件路径、API 与代码标识符、协议关键字和框架固定标记保持原样。引用必须保留的英文固定标记时，应在相邻位置提供简体中文说明；不得照抄基础模板的英文标题作为最终文档标题。

### 真实 TDD
新增或修改可单测行为及修复缺陷时，先编写测试并实际运行，确认测试因预期行为尚未实现而失败，再编写最小实现使测试通过，随后按需重构并回归验证。依赖、环境或语法错误不能作为有效的 Red；不得将事后补写测试宣称为 TDD。

### 可计量新增业务逻辑测试覆盖率
对仓库现有工具能够可靠采集的新增或修改自有生产代码可执行业务逻辑，单元测试覆盖率不低于 80%；优先采用语句或分支覆盖率，现有工具仅提供行覆盖率时可使用行覆盖率。纯声明式界面（包括 QML）、生成代码、资源和配置不纳入百分比分母，但相关属性、绑定、信号、状态变化及关键用户场景必须通过自动化行为测试；复杂业务逻辑应优先移入可单测模块。无可靠采集能力时明确记为不适用或能力缺口，不得填成 0% 或 100%，也不得用 qmlprofiler 等性能分析事件作为覆盖率证明。

### 有效测试与验证
测试必须调用真实被测生产逻辑，包含能识别错误行为的断言并实际发现和执行。禁止占位成功、恒真断言、mock 掉被测核心与静默跳过；未实际执行测试不得宣称通过。关键控制逻辑采用可恢复的反向验证或适用变异测试。

### 来源与事实核实
知识库与源码说明现状，已确认需求定义期望；关键结论记录来源与适用版本，未知必须明确，现状缺陷不得自动固化为规范。
正文开头增加“评审摘要”，显示任务规模、依赖、阻塞项、需确认内容和各类任务数量；不另建与正文重复的测试汇总表。
保持按用户故事组织；每个故事内部依次设置“测试任务（先行）”“实施任务”“验证任务”，不得把测试集中到远离需求的统一阶段。每条任务在官方 ID、`[P]`、`[USn]` 之后标记一个类型：`[测试]`、`[实现]`、`[验证]`、`[准备]` 或 `[文档]`。测试任务写明层级、目标行为、测试入口和关键断言，验证任务写明实际命令或可观察结果；不另建重复汇总表。
所有面向人的标题、小标题、表头、任务类别和状态说明使用当前语言规则；命令、路径、代码标识符和框架固定标记保持兼容。
记录来源、适用版本、关键差距与待决定事项。保持该阶段原有职责，不将未执行验证标为通过。

## 故事内任务组织

保留官方按用户故事组织的结构，在每个故事内依次设置“测试任务（先行）”“实施任务”“验证任务”，不将测试集中到统一末尾阶段，也不另建重复汇总表。所有任务在官方 ID、可选 `[P]` 和适用的 `[USn]` 之后增加一个类型标签：`[测试]`、`[实现]`、`[验证]`、`[准备]` 或 `[文档]`；共享准备任务没有故事标记时仍须有类型标签。`[P]` 表示可并行，`[USn]` 表示所属用户故事。

测试任务写明测试层级、目标行为、被测生产入口、测试文件路径和能识别错误行为的关键断言。新增或修改可单测行为及缺陷修复，先编写并实际运行测试，确认因预期行为尚未实现而失败，再实施最小实现并回归；依赖、环境和语法错误不是有效的预期失败。测试必须实际发现、执行真实生产逻辑，不得以恒真断言、核心逻辑替身或静默跳过充数。关键控制逻辑安排可恢复反向验证或适用变异测试，不把特定现有功能脚本当作通用验证。

验证任务写明实际命令或可观察结果及对应范围；涉及数据或消费契约变更时，核对受影响标识、引用和双语词条并执行适用契约校验。覆盖率按计划中的有效政策和实际可靠采集能力执行；能力不足时安排必要建设任务，不新增 CI 接入或强制报告任务。未执行不得标记通过，测试命令和结果在对话中简述。

示例格式，仅示意结构，生成时替换为实际任务与路径：

### 测试任务（先行）
- [ ] T001 [P] [US1] [测试] 在 `[测试路径]` 添加[层级]测试，调用 `[生产入口]`，验证[目标行为]并断言[关键结果]。

### 实施任务
- [ ] T002 [US1] [实现] 在 `[实现路径]` 实现[故事行为]。

### 验证任务
- [ ] T003 [US1] [验证] 执行 `[实际命令]`，确认[可观察结果]。

复用 `spec.md` 的 UI 参考及原资源，不重复复制图片；涉及文档移动时核对相对引用。
