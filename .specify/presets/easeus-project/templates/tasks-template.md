## 故事内任务增补

每个故事依次组织“测试任务（先行）”“实施任务”“验证任务”，按优先级和真实依赖推进，不把测试集中到统一末尾阶段，不另建重复测试汇总表。基础模板中的测试可选示例不能取消本次有效规则对可单测行为的要求；纯重构、配置和纯视觉调整按其适用方式安排，说明不适用测试先行的原因。

每条任务在官方 ID、可选 `[P]`、适用 `[USn]` 后增加一个类型标签：`[测试]`、`[实现]`、`[验证]`、`[准备]` 或 `[文档]`。共享准备项无故事标记时仍标类型；`[P]` 仅用于无依赖且不会争用同一文件的任务。类型标签不替代执行者或混合任务 `Type`。

## UI 任务依赖增补（仅适用故事）

沿用当前规格的 UI 分类、轻量／完整模式及基线；非 UI 不生成截图或 UI Gate 任务，待确认先澄清。当前阶段只生成任务，不自动执行后续阶段。

完整模式在相应故事内部安排：UI Gate 1 所需设计及映射确认 → 结构与主要控件 → 实际运行与当前截图 → 对照确认基线 → 修正阻断和重要偏差 → 剩余业务逻辑 → 交互及适用视觉回归。前置测试仍在实现之前；初步视觉验证项可按依赖紧邻相关实施项执行，故事末尾保留最终验证，不能让分组标题掩盖实际执行顺序。

首轮运行的最小必要数据按需列 `[准备]` 项，模拟状态明确标注且不替代最终集成。UI Gate 2 未运行、证据不足或仍有重要偏差时保持待验证／未通过，依赖它的后续业务实现阻塞，独立任务可继续。轻量模式在局部调整后完成对应验证，不生成空分组或完整附加文档。

复用计划中的 `src/views/`、`src/features/`、原生控件和 `src/styles/` 映射，规格中的设计来源及原图片不重复复制。截图沿用项目约定目录；在现有验收或任务必要位置记录页面／状态、候选版本及未提交范围、环境、验证者和证据引用。实际对比检查布局、组件、颜色、字体、尺寸、间距与状态；交互另用操作或行为测试。没有运行或看图能力时等待适用工具或人工验证，不以旧截图、设计图、构建成功冒充通过。

设计或实现改变时保留任务 ID 和有效成果，只重开受影响项及验证，核验旧截图是否失效；文档修订不自动授权编码。

## 条件式人工交接与执行

先读取现有验收、审批、发布约定及当前规格验收场景。默认不新增最终人工验收；只为已有约定或明确需求生成必要人工测试、评审或验收，已有覆盖不重复。负责人或发布影响不明时澄清。可在其他环境自动执行、但本机缺少设备、数据或权限的任务仍归 AI／`AUTOMATED_TEST`，记录 `Blocked reason`；失败或缺失实现不转成人工任务，不降低启用门槛。

需要混合任务或显式依赖时，才在现有 `tasks.md` 写入 `<!-- repo-sdd:hybrid-tasks:v1 -->`。`[AI]` 或无执行者标记由 Agent 执行，人工用 `[MANUAL]`，人工测试用 `[MANUAL] [TEST]`；这些标记置于类型标签之后，保留原生 ID、`[P]`、`[USn]` 和复选框。缩进字段名保持固定，字段值使用简体中文：

- `Type`：`DEVELOPMENT`、`AUTOMATED_TEST`、`MANUAL_TEST`、`REVIEW`、`ACCEPTANCE` 或 `OTHER`。
- `Dependencies: T010, T011`：仅列真实前置任务。
- 人工项填写 `Owner`、`Environment`、`Reason`、`Steps`、`Expected`、`Evidence` 和 `Required for release: true` 或 `false`；默认阻塞发布，`Evidence` 指向既有记录位置。确需正式签收才设置 `Final acceptance: true` 并关联前置任务。

不新增平行任务文件、工作项或证据包；无人工任务不输出空分组。明确停用时保留 `<!-- repo-sdd:hybrid-tasks:v1 {"enabled":false} -->` 并按原生规则执行；旧清单未经确认不转换。

执行前读取整份清单。启用混合任务时，先核实当前 Spec Kit 项目指南中的运行组件路径，执行 `workflow/run.ps1 inspect-tasks --tasks <仓库相对路径>`，或同目录 `python -B runtime.py inspect-tasks --project . --rules <当前规则快照> --tasks <仓库相对路径>`。可用 `--story US1`、`--phase <标题>`、`--task-id <ID>`（可重复）选批次，前置依赖仍跨批次检查。仅执行 `ready_ai`，完成后更新 AI 复选框并重算；人工项及依赖未完成人工项的任务保持未完成，继续独立项。非法依赖或循环须报告并修正，不假装完成。旧清单先读其原有交接约定，不凭自由文本跳过原生任务。

交接在已有位置列明已完成／剩余 AI 数、待人工项、阻塞及原因、实际自动化结果和可交 QA 范围。`execution_batch_complete` 仅表示当前批次暂无可执行项，`implementation_complete` 核对整份清单的 AI 任务；最终交付仍满足原生全量完成条件。

人工通过后，由授权人员填写 `Tester`、`Execution date`（YYYY-MM-DD）、实际环境（有差异时补 `Actual environment`）、`Result: passed`、`Result evidence` 或已填写的 `Evidence`，再勾选。Agent 不代填人工结果或勾选。失败保持未勾选，记录 `Result: failed`、`Issue`、`Reproduction` 和证据，增加 `Related to: <人工任务 ID>` 修复任务并复验。延期须按既有流程批准，记录 `Required for release: false`、`Deferred by`、`Deferred until`、`Deferral reason`，保留待验收状态。

最终先核对实现差距及真实测试，实际完成复核后才在适当已完成任务记录 `Implementation review: passed`、`Reviewed revision: <inspect-tasks 返回的 revision>`；正式人工验收结果及复核修订由授权人员填写，无人工要求可复用已有 AI 验证项。`FINALIZED` 仅表示当前修订任务和验收记录齐备，测试、CI 和审批真实性由项目机制核验。需求变化保留历史并重新打开受影响项，只读询问不改状态，续做先核对剩余任务。

`analyze` 不把明确交接的测试当作遗漏；`checklist` 保持需求质量职责和原有门禁。`converge` 在人工未完成时报告 `Pending Manual QA`；仍有阻塞实现时不能报告全量 `Converged`。官方 Bug 沿用 `assessment.md`、`fix.md`、`test.md`，未执行用例不得写为 `Result: Passed`，不自动推进阶段。
