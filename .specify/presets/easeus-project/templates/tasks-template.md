## EaseUS：tasks 阶段规则与依据
使用当前规则快照和已评审项目约定；为适用规则记录落实方式及完成条件。

### 交互与产物语言
使用简体中文交互和编写自然语言产物；命令、标识符与固定标记保持兼容。

### 真实 TDD
新增或修改可单测行为及修复缺陷时，先编写测试并实际运行，确认测试因预期行为尚未实现而失败，再编写最小实现使测试通过，随后按需重构并回归验证。依赖、环境或语法错误不能作为有效的 Red；不得将事后补写测试宣称为 TDD。

### 新增生产代码单测行覆盖率
仅新增自有生产代码的单元测试行覆盖率不低于 80%；以本功能明确基线计算新增可执行行的未舍入汇总比值，不要求存量代码或全项目达到 80%。集成或端到端覆盖率不能替代该指标，无新增可执行行记为不适用。

### 有效测试与验证
测试必须调用真实被测生产逻辑，包含能识别错误行为的断言并实际发现和执行。禁止占位成功、恒真断言、mock 掉被测核心与静默跳过；未实际执行测试不得宣称通过。关键控制逻辑采用可恢复的反向验证或适用变异测试。

### 来源与事实核实
知识库与源码说明现状，已确认需求定义期望；关键结论记录来源与适用版本，未知必须明确，现状缺陷不得自动固化为规范。
记录来源、适用版本、关键差距与待决定事项。保持该阶段原有职责，不将未执行验证标为通过。






## 项目任务生成补充

本次 effective_rules 已启用真实 TDD。基础示例中的测试可选说明不适用于新增或修改可单测行为及缺陷修复；按计划生成实际任务，保留原有任务编号、故事分组和路径格式。

### 测试先行依赖

每个适用行为的任务依赖应体现：必要测试能力准备 → 编写并实际运行针对真实生产逻辑的测试，确认因预期行为未实现而失败 → 最小实现并运行对应测试通过 → 按需重构和回归。实现任务必须依赖相应测试先行步骤，不将两者标为可并行。

测试失败若来自依赖、环境或语法问题，应先修复执行条件，再确认行为失败；不得把事后补测记作 TDD。不可单测的变更说明适用验证方式，不制造占位测试。

### 按实际影响生成验证任务

- 单测：使用 npm test -- [实际测试路径或筛选参数]，确认测试被发现、执行并调用真实生产逻辑；关键控制逻辑安排可恢复反向验证或适用变异测试，结束后恢复并回归。已有功能专用变异脚本仅在适用时复用。
- 数据或词典：安排 npm run validate:data，并检查本功能涉及的标识、引用及双语一致性。
- 构建：安排 npm run build；涉及浏览器流程时，在成功构建及所需浏览器就绪后执行 npm run test:e2e -- [实际选择参数]。
- 双语与兼容：按计划安排中文、英文、移动端及确认浏览器范围的实际检查；缺少必要能力时先安排最小建设任务，再安排依赖它的验证，不新增 CI 接入任务。
- Function：涉及服务端能力时使用计划确认的 Function 环境验证；前端 mock 或 Vite preview 不替代真实服务路径验证。
- 覆盖率：使用计划明确的功能基准及已有 npm run coverage:baseline、npm run test:coverage、npm run coverage:added 入口，补全真实参数并显式指定输出位置；仅核算新增自有生产代码单测可执行行，未舍入汇总比例至少 80%，无新增可执行行为不适用。不得固定使用历史功能基线或新增基线快照任务。

上述条目是任务生成维度，按功能适用性合并到现有任务中，不逐项机械增建任务。实际命令与结果在对话中简述；任务状态仅在对应工作实际完成后更新。开发产物以 Spec Kit 原生文档、代码、测试及必要任务状态为主，不增加独立 Red/Green 收据、evidence 目录、追踪映射、逐任务验收说明、截图或 HTML 报告任务。
