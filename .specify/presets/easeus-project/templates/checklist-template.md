## EaseUS：checklist 阶段规则与依据
使用当前规则快照和已评审项目约定；为适用规则记录落实方式及完成条件。

### 交互与产物语言
使用简体中文交互和编写自然语言产物；命令、标识符与固定标记保持兼容。

### 真实 TDD
新增或修改的可单测行为与缺陷修复执行真实 Red → Green → Refactor，记录实际失败与通过证据，不伪造历史 Red。

### 新增生产代码单测行覆盖率
仅新增自有生产代码的单元测试行覆盖率不低于 80%；以本功能明确基线计算新增可执行行的未舍入汇总比值，不要求存量代码或全项目达到 80%。集成或端到端覆盖率不能替代该指标，无新增可执行行记为不适用。

### 有效测试与完成证据
测试必须调用真实被测生产逻辑，包含能识别错误行为的断言并实际发现和执行。禁止占位成功、恒真断言、mock 掉被测核心、静默跳过与无证据勾选完成；关键控制逻辑采用可恢复的反向验证或适用变异测试。

### 来源与事实核实
知识库与源码说明现状，已确认需求定义期望；关键结论记录来源与适用版本，未知必须明确，现状缺陷不得自动固化为规范。
记录来源、适用版本、关键差距与待决定事项。保持该阶段原有职责，不将未执行验证标为通过。






## 项目需求质量评审维度增补

按本功能相关性生成条目并与既有 CHK 编号连续衔接，所有新增条目保持未勾选。每项引用具体需求、场景或章节；缺失、歧义、冲突和假设分别使用 [Gap]、[Ambiguity]、[Conflict]、[Assumption]。不适用维度记录理由。

| 维度 | 应生成的需求质量问题 |
| --- | --- |
| 产品边界完整性 | 是否明确静态快照的含义，以及实时化、自动同步和官方信息承诺的范围？ |
| 可选能力独立性 | 相关需求是否明确 AI 未配置或不可用时核心浏览的验收条件，并区分演示与生产能力？ |
| 行为清晰度 | 用户可观察结果是否明确；双语、主题、导航和状态保留要求是否一致且可判定？ |
| 场景覆盖 | 相关加载、空数据、失败、重试、存储不可用及连续异步操作的需求是否完整，或明确排除？ |
| 兼容承诺 | 是否区分已承诺支持范围、当前验证配置和待决定的浏览器最低版本？ |
| 来源可信度 | 关键结论是否记录真实来源、适用版本与核实状态；源码现状是否与已确认期望分开？ |
| 验证设计充分性 | 计划是否定义真实生产逻辑、可识别错误的断言、测试发现与执行证据，以及适用的反向验证或变异方案？ |
| TDD 依赖清晰度 | 任务是否定义真实 Red → Green → Refactor 的依赖及证据要求，并明确已有实现的历史证据边界？ |
| 覆盖率口径一致性 | 是否定义本功能实施前基线、新增自有生产可执行行范围、单测 C/D 汇总口径、80% 门槛及 D=0 不适用语义？ |
| 能力缺口可处理性 | 当前验证能力不足时，计划和任务是否明确建设内容、前置依赖及完成证据？ |
