## 项目评审维度

按需求选择完整性、清晰性、一致性、可验证性、范围边界、异常、兼容性、数据契约、双语语义、AI 降级及适用 UI 维度。每项只问一个可回答的问题，保留顺序 `CHKxxx`，定位到实际 `FR-xxx`／验收 ID 和文档位置，注明优先级及简短理由；缺失需求用准确的缺口位置定位。不要把多个问题用“且”合并，也不复制规格正文。

按需选择下列问题方向，生成时拆成独立条目并替换引用：

- 静态信息：相关需求是否明确静态快照属性？
- 数据契约：某一受影响标识的唯一性约束是否明确？
- 引用关系：某一受影响引用的无效值处理是否明确？
- 双语：相关需求是否界定两种语言的同一业务含义？
- 路由：相关需求是否明确参数缺省结果？
- 持久化：相关需求是否明确写入失败时的用户行为？
- AI 降级：相关需求是否明确 AI 不可用时应保持的核心浏览能力？
- 兼容性：某一契约变更是否说明迁移影响？

条目格式示意：

- [ ] CHK001 [优先级：高] [维度：可验证性] [FR-xxx／验收 ID；spec.md 对应位置] 该需求是否定义可观察的成功结果？（理由：[本次评审需要解决的单一风险]）

## UI 需求质量评审（仅 UI 范围）

沿用规格的 UI／非 UI／待确认结论及依据。非 UI 不生成 UI 条目；待确认先报告缺口。UI 评审按实际范围将以下方向分别生成单问题条目：设计读取状态是否明确、设计版本是否可复核、确认范围是否明确、某项状态的验收是否可观察、某个组件映射是否可追溯、某项视觉约束的验证方式是否可行、某个交互的行为验收是否明确。

核对需求、设计基线、组件映射、任务和验收的对应关系；按需检查中英文文案、深浅主题、视口及键盘行为需求的清晰性，不从现状自动增加产品承诺。需求已有 UI 图片时沿用 `spec.md` 的原引用，分别检查相关文字依据、图文冲突或来源缺口；图片不作为当前运行通过证明。

UI Gate 1 的需求与确认条件、UI Gate 2 的验证计划可作为需求完整性问题，但不把“实际截图已取得”或“交互测试已通过”冒充需求质量结论。只读一致性分析只报告问题；明确获准修改文档后才按原生范围更新，不自行推进实施或审批。

## 清单状态与交接边界

`[x]` 只表示评审者确认该需求质量标准满足，不表示实现完成、自动化测试通过或人工验收通过。未确认、需澄清或需修订的条目保持未勾选；保留基础模板的评审所有权、implement 门禁和原生清单生命周期，不代改评审标记。

人工测试用例及执行字段留在已有任务／验收位置；不搬入本清单，不重复新增最终人工验收，不把明确交接的验证认定为缺失实现。实际测试和实现差距由原生验证及收敛流程处理。
