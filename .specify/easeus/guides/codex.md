# Spec Kit · Codex SDD 使用指南

这份指南用于在当前仓库开展开发。部署完成不代表业务测试通过。

## 第一次开始

1. 在 Codex 中打开当前仓库根目录，重新打开会话，让 Agent 重新发现项目技能和 MCP 配置。
2. 确认技能列表中出现下方入口。示例中的需求描述请替换为实际任务。
3. 每次明确任务和验收条件；有多个进行中任务时，指定任务 ID 或规格路径。

推荐从任务分流开始：默认只分析任务与风险，在对话中推荐流程，不创建任务文件、不推进阶段或修改代码。

```text
$sdd-speckit-start 分析以下目标并推荐流程：<目标、边界与验收条件>
```

查看推荐后，明确要求继续或调用所推荐的入口，才创建任务和推进。单独调用 start 或描述“实现某功能”不等于授权执行；如果希望一次完成，需要明确说明“分析推荐后按推荐流程继续执行”。

## 完整新功能流程

按顺序推进；只请求分析或计划时，Agent 不应直接进入实施。

### 定义需求

整理目标、范围、验收场景，生成 spec.md。

```text
$speckit-specify <功能目标与验收条件>
```

### 澄清需求

解决规格中的关键歧义，并更新 spec.md。

```text
$speckit-clarify <明确的功能规格路径>
```

### 制定计划

结合当前仓库形成 plan.md 和必要设计。

```text
$speckit-plan <功能规格路径及技术约束>
```

### 拆分任务

生成带依赖和验证步骤的 tasks.md。

```text
$speckit-tasks <功能目录>
```

### 检查一致性

检查需求、计划和任务是否一致，先解决重要缺口。

```text
$speckit-analyze <功能目录>
```

### 实施与测试

按启用规则实施，运行真实测试并记录结果。

```text
$speckit-implement <功能目录>
```

### 实现收敛检查

按全功能规格、计划、任务和实际实现检查差距，保留原生追加任务职责，不强制逐批运行。发现问题后回到对应阶段修正，再次运行收敛检查。

```text
$speckit-converge <功能目录>
```

实现收敛后，按项目约定继续验收。仍有人工任务时报告“待人工验收”，由授权人员执行并记录结果。最终完成需满足项目约定的全部必需验收条件。

## 精简、可评审的文档

规格写行为与验收，计划写设计与取舍，任务写可检查的工程成果和完成条件。摘要只突出变化、关键决定、待确认项与风险；跨文档引用已有内容，不重复背景或全文规则。

不设需求、故事或任务数量上限。单位、边界、异常、兼容要求必须明确，不能用“合理”“符合预期”代替。仅保留适用章节和任务，保留稳定 ID；TinySpec 继续使用单文件，不新增阶段报告或证据包。

Studio 检查生成配置的结构；功能文档仍由 Agent 结合实际内容评审。重复表达、粒度不当等语义问题应提出位置与建议，确认后再修改，不能静默合并、删除或重编号。

## 按授权范围分批实施

未指定批次时沿用当前授权范围，按依赖分批实施和验证，不默认逐批请求人工批准。明确要求只执行某批时，完成后停止；范围扩大、需求不明确或真正阻断时再处理。

```text
$speckit-implement 本次只执行 specs/<功能>/tasks.md 的 US1；检查完整清单的依赖，不扩展到其他任务，完成后停止并说明实际测试、阻塞和下一步。
```

<summary>批次检查命令与返回状态</summary>

在仓库根目录运行只读检查；示例中的路径和任务 ID 替换为清单实际内容：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ".specify/easeus/workflow/run.ps1" inspect-tasks --tasks "specs/<功能>/tasks.md" --task-id T001 --task-id T002
```

也可用 --story US1 或 --phase "阶段标题"。重复 --task-id 取并集，不同参数取交集；父级阶段包含子章节。重名阶段返回候选位置，改用明确任务 ID。未知 ID、空匹配和结构或依赖错误明确报错，不回退到全部任务。

先从全部任务确定范围，包括已经完成的任务；范围外未完成的前置任务仍会阻塞，不自动扩大本轮范围。没有混合任务标记的旧清单也支持选择，但仅按原生复选框计算，不自动赋予人工或延期语义。

返回契约 result_version: 2：selected_tasks 是选中 ID；batch_remaining_ai、batch_pending_manual、batch_completed_ai 分别是范围内剩余 AI、待人工和已完成 AI；ready_ai 与 blocked 是本批可执行项和阻塞原因。

batch_status 按优先级为 invalid（错误）、ready（存在可执行 AI）、blocked（AI 尚未完成但均阻塞）、pending_manual（AI 已完成人工仍待办）或 complete（选中任务全部完成）。混合情况仍列出全部阻塞和人工待办。

batch_ai_complete 仅表示选中范围的 AI 任务全部完成。execution_batch_complete 已修正为选中任务全部完成且没有结构或依赖问题；不能继续按旧版“暂无可执行任务”理解。implementation_complete、remaining_ai、pending_manual 等仍以全清单计算。

退出码 0 只表示检查成功，不代表批次完成。complete 仅表示任务记录完成，verification 保持 unverified；它没有核验业务测试、覆盖率或 CI。这些约定不是文件权限沙箱或审批系统。

</details>

Agent 不勾选人工任务；无关人工项不阻止独立工作，依赖未完成的任务继续阻塞。每批在对话中说明范围、任务结果、真实测试、阻塞和下一步，不另建阶段报告。

## 交给测试人员执行的用例

默认不增加最终人工验收任务。先看项目宪法或已有发布约定，再根据本功能规格安排必要的人工测试、评审或验收。已有人工任务覆盖验收时直接沿用。

```text
$speckit-tasks <功能或变更名称>；根据项目约定，将必须在实体设备上操作的验收用例加入原任务清单，列明执行角色、步骤、预期和依赖。
```

Agent 可继续独立任务，依赖人工结果的任务保持阻塞。人工通过后由授权执行者在原任务填写执行人、日期、结果和记录位置，再勾选。失败时保留未勾选并关联修复任务。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ".specify/easeus/workflow/run.ps1" inspect-tasks --tasks "specs/<功能>/tasks.md"
```

任务检查分别报告当前可执行任务、实施完成、待人工验收和当前修订的记录状态。测试、CI 及发布审批按项目原有流程核验。

## 涉及 UI 的功能

Agent 先读取本次 spec.md、prd.md 或原生需求工件，给出 UI／非 UI／待确认结论和依据；你可以覆盖结论，并选择轻量或完整模式。非 UI 功能沿用原流程。

UI 功能先用 OpenDeepWiki 理解业务和架构，再用 CodeGraph 定位组件及调用关系，最后核验当前源码。设计输入可来自 Figma、本地截图、现有页面、组件规范或文字说明；Figma 可选，但提供的设计材料必须实际读取，不能只保存链接。

实施前通过 UI Gate 1，确认设计输入、验收条件、组件映射和验证方式。完整模式先实现可运行界面并在 UI Gate 2 对照实际截图或约定证据，修正重要偏差后再继续剩余逻辑；局部低风险修改可采用轻量模式。两个 Gate 是 Agent 检查与必要人工确认，不是程序强制审批。

偏差按需求、方案、实现或设计变更分类，只更新受影响的工件、代码和测试；保留仍然有效的任务及实现，不通过修改正确需求来迁就错误界面。

### PRD 已包含 UI 图片

向 Agent 提供 PRD 文件路径及本次功能范围。仓库内图片复用原文件；仓库外已提供资源仅导入必要图片，避免重复副本。生成的规格显示 UI 参考、PRD 来源与关联验收条件。

图片的版本、日期及批准状态未提供时标为“未注明”，不自行认定设计已批准；图片与正文冲突时写入原文档待确认项。

远程图片不默认下载；需认证或无法查看时说明原因，不将凭据写入文档。无相关图片时不增加空章节，也不自动生图。

```text
$speckit-specify 以 docs/requirements/prd.md 为输入，只处理其中的<本次功能范围>；保留相关 UI 图片引用与来源，将已有行为要求转写为可验证验收条件。
```

### 验证与完成检查

核对验收场景、实际修改与真实测试结果；任务完成和验证通过分别判断。测试未运行或失败时如实披露，不把环境错误当作有效 Red；覆盖率与质量检查沿用仓库已有方式，只对工具可可靠计量的可执行业务逻辑计算百分比。

使用统一入口创建或登记的任务，在结束前核对原生产物和任务：

```text
$sdd-speckit-resume 继续 specs/tiny/<名称>.md，直接核对任务复选框和完成条件，不创建 work-item.json
```

```text
$sdd-speckit-resume 继续任务 <任务ID或 work-item.json 路径>，核对当前产物、执行适用的完成检查并说明剩余缺口
```

## Bug、小改动与需求变更

当前功能的实现缺陷若预期已经明确，关联原任务及已有 Issue，安排复现测试、修复和回归，不必另建一套缺陷管理记录。需求歧义或确需改变行为时先确认影响，再更新相关规格；不通过改规格、删任务或虚构结果掩盖缺陷。

用户明确调用正式 Bug 流程时使用下方已部署入口；Studio 仅提供约定与指南，不管理缺陷、严重程度或审批。

明确要求修复或实施后才执行；仅诊断或分析时保持只读。Spec Kit quick 只创建 `specs/tiny/` 下的一份 Markdown，直接从任务复选框续做，不生成 `work-item.json`。 change 先分析已有任务的影响，具体更新方案获准后才更新文档，不自动继续实施。resume 继续指定的已有任务；只询问进度时不推进，也不创建替代任务。

### 处理小改动

```text
$sdd-speckit-quick 处理 <边界清楚的小改动>；验收条件 <条件>；使用单文件 TinySpec
```

### 修改实施中的需求

```text
$sdd-speckit-change 为任务 <任务ID> 分析需求变更 <内容>，先展示影响和拟更新方案，确认后再更新
```

### 继续已有任务

```text
$sdd-speckit-resume 继续任务 <specs/tiny 文件、任务ID或 work-item.json 路径>，核对状态和已有产物
```

### 修复 Bug（官方流程）

不使用 Studio 包装入口。三个官方技能使用同一个 slug，并且每一步完成后审阅产物，再由用户明确调用下一步；不会自动从诊断推进到修改代码。

诊断问题并写入 assessment.md：

```text
$speckit-bug-assess <问题、预期行为和复现步骤> slug=<bug-name>
```

按已审阅的诊断实施修复并写入 fix.md：

```text
$speckit-bug-fix slug=<bug-name>
```

复现并验证修复，写入 test.md：

```text
$speckit-bug-test slug=<bug-name>
```


## 实际测试与有效规则

按当前启用规则执行真实 TDD：先测试并确认预期失败，再实现通过，按需重构与回归。停用 TDD 时不强制恢复。
使用仓库自己的测试命令，按修改范围验证，在对话中说明命令、实际结果和未验证事项。覆盖率阈值以当前规则为准，沿用项目已有工具与 CI，只对工具可可靠计量的可执行业务逻辑计算百分比。纯声明式 UI（包括 QML）等不可可靠计量内容采用自动化行为测试；qmlprofiler 等性能分析事件不能作为覆盖率证明。
主要交付为规格文档、生产代码、测试和必要工作流状态；不默认创建 evidence、阶段收据、源码副本、验收总结或 HTML 报告。UI 任务仅按已确认的验证方案保留必要界面证据，非 UI 任务不增加截图要求。
finish 的成功只表示实施流程已完成，测试、覆盖率和 CI 状态仍为未核验。本应用不配置或同步 CI。

本仓库当前启用的工程规则：

- 交互与产物语言：面向团队评审的自然语言使用简体中文，包括标题、小标题、表头、任务类别和状态说明；命令、路径、代码标识符及框架固定标记保持原样。必要术语首次出现时提供简短解释，后续不重复翻译；遵守项目已有的公共 API、国际化和文档约定，不照抄基础模板英文标题作为最终自然语言标题。
- 真实 TDD：新增或修改可单测行为及修复缺陷时，先编写测试并实际运行，确认测试因预期行为尚未实现而失败，再编写最小实现使测试通过，随后按需重构并回归验证。依赖、环境或语法错误不能作为有效的 Red；不得将事后补写测试宣称为 TDD。纯重构先确认已有测试通过，再重构并回归，不人为制造失败；遗留代码可先补描述现状的特征测试。缺陷无法稳定复现时先调查并说明限制，不编造失败；探索性原型、环境配置及纯视觉调整采用适用验证。不适用或无法可靠执行测试先行时说明原因及替代验证，不得宣称为 TDD。
- 可计量新增业务逻辑测试覆盖率：对本次新增或修改、可可靠采集的自有可执行业务逻辑，按项目明确的单元测试覆盖率指标和变更范围检查，默认门槛为 80%。计划中明确采用行、语句或分支覆盖率及计算范围，不混用指标，不以全项目覆盖率代替变更范围指标；关键行为、边界和错误路径不能因达标而省略测试。纯声明式 UI、生成代码、资源和配置可排除百分比分母，说明理由并采用适用的行为验证；不按文件类型整包排除，QML 内可执行 JavaScript 业务逻辑仍须单独评估，复杂逻辑优先移入可单测模块。无可靠采集能力记为未核验／能力缺口，不视为不适用，不得填成 0% 或 100%；qmlprofiler 等性能分析事件不能作为覆盖率证明。
- 有效测试与验证：测试必须调用真实被测生产逻辑，包含能识别错误行为的断言，并实际被发现和执行。禁止占位成功、恒真断言、替换被测核心逻辑与静默跳过；允许合理使用测试替身隔离网络、时钟、数据库、文件系统等外部依赖，并按风险补充集成验证。未实际执行或失败的测试不得宣称通过。对高风险或断言有效性存疑的逻辑，按需采用可恢复的反向验证或变异测试，不要求每次修改都执行。
- 来源与事实核实：知识库与源码说明现状，已确认需求定义期望；仅对影响需求、设计或兼容性判断的关键结论，在对应原生产物中简短记录必要来源与适用版本，不重复复制源码、知识库内容或工程规则全文。未知明确说明，现状缺陷不得自动固化为规范；知识库与当前源码不一致时指出差异，不仅凭更新时间推断谁正确。
