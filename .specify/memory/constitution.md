# WorldCup2026 宪法

## 核心原则

### I. 本次启用的工程规则不可降低

以下受保护区块完整规定本次适配启用的工程规则。项目补充、模板示例、历史文件和工具默认值不得降低或删除这些条款；未启用的工程门槛不得自动恢复。

### II. 静态快照边界与来源可追溯

赛事信息保持静态快照边界。数据及面向用户的说明必须准确表达来源、适用范围和已知限制，不得将学习和演示用快照表述为实时比分或官方权威信息。数据更新须记录可追溯来源；改变实时性或权威性承诺前，必须先取得明确的需求确认。

### III. 数据引用与查询语义一致

赛事数据变更必须维护比赛标识唯一性、球队与场馆引用完整性，以及积分榜和相关赛事数据之间的一致性。页面、搜索和 AI 数据查询引用同一赛事概念时，必须保持一致的数据含义；涉及数据契约变更时，须同步评审受影响的生产逻辑、数据和校验规则。

### IV. 核心赛事浏览独立于 AI 服务

核心赛事浏览必须独立于可选 AI 服务。缺少 AI 配置、第三方服务不可用或聊天初始化失败时，不得阻断核心赛事浏览。涉及 AI 集成的变更须明确其依赖边界和降级行为，不得把模型回答作为赛事快照的权威替代。

### V. 双语语义一致

中文和英文界面必须保持赛事概念、状态、操作结果与数据说明的语义一致。新增或修改面向用户的内容时，须同时评审两种语言及相关词典引用，避免语言切换改变业务含义。

## 项目约束与适用范围

- 本宪法适用于 WorldCup2026 的规格、设计、任务、实现和评审。本次采用 Spec Kit 工作流。
- 原生 JavaScript、ES Modules、静态数据和可选 Netlify Functions 是当前架构事实；这些事实不自动构成永久禁止架构演进的规则。架构变化须说明对已批准项目原则的影响。
- 浏览器支持政策已接受；具体最低版本和移动设备范围仍由用户逐条评审确定。不得将 Vite、Playwright 或浏览器默认值表述为已批准的支持承诺。
- 工程规则以本次 effective_rules 和 effective_policy 快照为唯一来源。新增覆盖率 HTML 和需求 TDD HTML 报告均未启用；仓库中已有报告脚本或 CI 步骤不自动成为宪法要求。
- 知识库用于辅助定位和理解；提交对应关系不明、索引漂移或源码与文档冲突时，必须记录限制，并核对当前文件与已确认需求。

## 开发流程与遵循检查

1. 规格应明确用户场景、验收条件和相关项目边界；计划应将适用宪法条款映射到 Constitution Check，并在研究前及设计完成后检查。
2. 任务须落实本次启用的 TDD、有效测试和新增生产代码覆盖率规则。模板中“测试可选”等示例不得削弱适用的受保护条款。
3. 评审须核对静态数据边界、引用一致性、AI 独立性和双语语义，并记录适用条款的证据或不适用理由。
4. 验证记录须区分已执行、未执行、失败和受阻，标明适用源码版本及覆盖率比较基线；不得把工具配置、测试文件存在或历史报告当作当前验证通过的证明。
5. 发现现状差距时，记录影响和后续处理，不得把历史缺陷固化为强制行为，也不得以局部例外降低受保护规则。

## 治理

本宪法在本次有效规则及已批准需求范围内约束项目实践。项目指引和工作流产物须与其保持一致；另一框架的受管区段不适用于本次适配，不能覆盖本次规则快照。

修订必须记录变更条款、理由、来源、兼容性影响以及必要的迁移安排，并经用户评审批准后生效。涉及新增产品承诺或治理政策的建议必须先取得用户批准。受保护规则的变更只能依据经确认的新有效快照，不得通过项目例外降低当前启用条款。

采用语义化版本：不兼容的原则删除、重定义或治理义务变化提升 MAJOR；新增原则或实质扩展义务提升 MINOR；不改变义务的措辞澄清提升 PATCH。

本候选暂按首次建立的 1.0.0 表达：当前文件不存在且未取得旧宪法正文，因此尚不能断言这是历史首次批准。向导应用前若发现历史宪法，必须保留真实批准日期，比较旧版本与条款差异；保留仍有效信息，对与当前有效快照冲突的历史规则提出显式修订，并重新评审版本变更，不得直接覆盖或静默继承。

首次批准和本次修订日期由向导在用户确认宪法评审时填写。版本及日期元数据不表示本草稿已经生效，也不表示项目已经完成合规验证。
