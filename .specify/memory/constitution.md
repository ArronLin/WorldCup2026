## 核心原则

### 一、赛事数据契约一致性

赛事数据变更必须维持已确认数据契约中的标识唯一性、实体引用和派生结果一致性。

### 二、核心浏览独立可用

可选 AI 问答不可用时，核心赛事浏览必须仍可独立使用。

### 三、交互状态一致性

异步加载或界面重新渲染后，用户可见状态必须对应当前有效操作，不能由过期操作结果覆盖。

## 适用边界与补充说明

当前产品边界为静态赛事信息浏览及可选 AI 问答。静态快照不代表实时或官方比赛信息；改变这一产品边界应先形成已确认需求。

兼容性评审范围采用已确认的浏览器与 Netlify Functions 运行边界；具体最低版本、浏览器矩阵和 API 兼容承诺仍待逐项评审。当前 Chromium 配置不构成其他浏览器兼容性的证明。

覆盖率百分比仅适用于工程规则定义的可靠可计量范围。现有工具按可执行语句起始行汇总的口径需在具体变更中说明，不能将其描述为完整分支覆盖率。当前快照未启用新增覆盖率 HTML 或需求 TDD HTML 报告要求。

## 开发流程与遵循检查

1. 规格阶段记录已确认需求、验收条件及尚未解决的事实；知识库和源码作为现状依据。
2. 计划阶段的 Constitution Check（宪法遵循检查）逐项判断适用条款，记录检查方式、证据和能力缺口；设计完成后再次检查。
3. 任务阶段将适用工程规则及项目原则映射到具体工作。实现方式、验证入口和兼容矩阵由相应变更计划确定。
4. 变更评审记录实际执行结果，明确区分通过、失败、未执行和不适用；未解决的违反项不能记为已遵循。

## 治理

本宪法是本次 Spec Kit 工作流的项目治理依据；工程规则唯一来源为当前有效规则快照。其他框架的受管区段、模板、默认规则和报告入口不适用于本次适配，不能覆盖本次快照。

修订须记录变更内容、理由、影响、版本变化及必要迁移安排，并由用户批准；指定负责人后更新审批职责记录。政策建议在批准前保持候选状态。

本次受保护工程规则不得通过项目补充、例外或实施计划降低或删除。其他项目条款如需例外，应记录范围、理由、风险、补救安排及审批结果，不得默认为普遍豁免。

规格、计划和变更评审应检查宪法遵循情况；发现冲突时显式记录并通过修订或纠正处理，不以代码现状自动改写规范。

版本采用语义版本：删除原则或作不兼容的治理变更增加主版本；新增原则或实质扩展要求增加次版本；不改变约束含义的澄清增加修订版本。在未恢复历史批准记录的前提下，本稿采用已批准的 1.0.0 初始基线，因此不能声称从某个历史版本升级。若发现历史批准记录，应先合并有效条款、保留真实首次批准日期，再评估版本变化。

日期由向导在用户确认宪法评审时填写；恢复的真实首次批准日期保持不变。
