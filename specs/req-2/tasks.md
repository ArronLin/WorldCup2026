# 积分榜排序任务清单

适用仓库为 `worldcup-2026`，实施分支为 `req/1-group-standings-sorting`。用户故事见 [功能规格](spec.md)，实施依据见 [实施计划](plan.md)、[研究记录](research.md)、[数据模型](data-model.md) 和 [交互契约](contracts/standings-sort.md)。`specflow.tasks.json` 保存同一批任务的稳定标识、需求与验收编号、文件范围及完成条件。共 6 项，全部待执行。

## 第一阶段 · 环境准备

T001 确认 Node.js 24+，按 `package-lock.json` 执行 `npm ci`，记录开始时间、结束时间与退出码。修改生产代码前记录变更前 Git 提交，或用 `npm run coverage:baseline` 建立源码基线。共用新检出的工作区时，T002 可同时编写测试，但须等 T001 的 `npm ci` 成功退出后才启动 Vitest。T005 检查 Chromium 是否可用，缺少时执行 `npx playwright install chromium`。

## 第二阶段 · 共用基础

冻结源码中的 `src/views/group-standings.js` 调用 `getStandings()`，按输入顺序渲染非空小组，四项统计使用普通表头，空值回退为零。T001 提供排序规则，T002 用真实视图记录行为缺失的断言失败。两项均完成后进入 T003。依赖安装、导入或测试收集出错时，先修复环境，再重新取得行为断言结果。

## 第三阶段 · 用户故事 1：按指标比较组内球队（P1）

- [ ] T001 [P] [US1] 在 `tests/standings-sort.test.js` 先测试再实现 `src/standings-sort.js` 的方向转换与稳定数值排序，字段见 `data-model.md` 的 `球队积分记录.points`、`球队积分记录.goalsFor`、`球队积分记录.goalsAgainst`、`球队积分记录.goalDifference`、`行的初始序号.组内从零开始的索引`。
- [ ] T002 [P] [US1] 在 `tests/group-standings-view.test.js` 用 jsdom 挂载真实 `standingsView`，验证四个按钮、方向、行序、焦点与缺失提示，在 T003 实现前运行并记录预期的断言失败。
- [ ] T003 [US1] 在 `src/views/group-standings.js` 接入原生排序按钮并移动本组原有球队行，按需调整 `src/styles/pages.css`，依据 `data-model.md` 的 `球队积分记录.code`、`球队积分记录.name`、`球队积分记录.position` 保留身份、名次及详情入口。

**独立验收**　在同一组依次操作四列，验证失球数首次升序，其余首次降序，再次选择翻转，切走切回恢复默认方向。每次同时核对完整球队顺序、唯一活动表头的 `aria-sort` 和可见箭头。用 2、9、10 与净胜球 2、0、-1、-3 检查两个方向的数值比较。用其他指标打乱并列队后切回，验证升降序均保留初始相对顺序。真实零参与比较，多个无效值均置后、显示本地化缺失提示并保持彼此初始顺序。空组继续省略，单队和全组同值仍更新方向。对照冻结输入核对球队集合、统计、原名次和行节点。T003 先复现 T002 的目标失败，最小实现后复跑同一用例及排序模块测试。

## 第四阶段 · 用户故事 2：分别比较不同小组（P1）

- [ ] T004 [P] [US2] 在 `tests/group-standings-view.test.js` 验证双组隔离和重挂载，按需修正 `src/views/group-standings.js`，字段见 `data-model.md` 的 `小组.组标识`、`小组.进入页面时的球队序列`、`小组.一个排序状态`、`小组排序状态.指标`、`小组排序状态.方向`。

**独立验收**　先操作 A 组，核对尚未排序的 B 组。再使 A 组按分数降序、B 组按失球数升序，改选并翻转 A 组指标，每一步均对照 B 组原有球队、统计、行序、活动表头和方向提示，并核对各行所属小组。断开再连接同一卡片，一次激活应只触发一次排序。重新进入页面时，各组恢复输入顺序及未选择状态。已有行为以特征测试确认，发现缺口时先取得目标断言失败，再修正并复跑。

## 第五阶段 · 用户故事 3：理解排序结果并继续浏览（P2）

- [ ] T005 [P] [US3] 在 `e2e/standings-sort.spec.js` 编写真实导航用例，仅用例编写可与 T004 并行；T004 完成后构建并验证 AC9、两种键盘操作、赛事说明及两种 AI 不可用环境下的四项排序。

**独立验收**　T004 完成后执行 `npm run build`，在包含其变更的独立预览上执行 `npm run test:e2e -- e2e/standings-sort.spec.js`。记录构建、预览及用例结果。T004 未完成时，T005 保持未完成。

1. **Enter 键**。从固定数据、尚未排序的页面开始，用 Tab 聚焦“分数”表头按钮。连续按两次 Enter，每次按键后分别检查。第一次应为分数降序、`aria-sort="descending"`、↓，第二次应为升序、`aria-sort="ascending"`、↑。
2. **空格键**。用独立用例重新进入同一未排序页面，用 Tab 聚焦“分数”表头按钮。连续按两次空格，每次按键后分别检查。第一次应为分数降序、`aria-sort="descending"`、↓，第二次应为升序、`aria-sort="ascending"`、↑。

两个用例的每一次按键都要验证恰好触发一次排序、焦点仍在原按钮、该组只有一个活动表头，并逐行比对固定输入对应的完整预期球队顺序。可在测试侧观察活动表头的方向写入次数。分别保存 Enter 和空格的执行结果。

用指针操作四列，核对中英文提示、原名次、资格样式、球队详情链接及静态演示快照说明。按 US2 的双组步骤执行 AC9，逐步比对 B 组。分别在 AI 未配置、受控 AI 请求已实际返回服务错误的条件下，从站点导航进入积分榜，逐项操作四列，检查完整数据、行序及方向，并验证排序期间新增 AI 请求数为零。

## 第六阶段 · 回归与覆盖率

- [ ] T006 通过 `package.json` 执行全量单测、数据校验、构建和独立预览浏览器回归，核算 `src/standings-sort.js`、`src/views/group-standings.js` 的变更分支覆盖率，并运行 `inspect-tasks` 核对交付状态。

**验证步骤与完成条件**

1. T004、T005 完成后，在当前工作区执行 `npm test`、`npm run build`。构建成功后记录工作区绝对路径、`dist/index.html` 及其引用的带哈希资源标识。确认 `127.0.0.1:4173` 空闲。端口已被占用时记录阻塞，待空闲后重试。
2. 仅为本次 Playwright 进程设置 `CI=1`，由 `npm run test:e2e` 启动独立预览并执行全量回归。保留预览启动日志和全量回归退出码，将预览实际返回的页面及资源标识与本次构建逐项核对。启动失败或版本不符时记录原因，修正后重跑。
3. 执行 `npm run test:coverage`，用 `npm run coverage:added` 对照 T001 基线。将 V8 分支明细与变更位置对应，纳入比较、方向转换、指标选择、有效性、界面状态和事件处理分支。记录基线、命中分支结果数、纳入分支结果总数及比值，默认门槛为 80%。低于门槛时补充有效单测并复跑。纯声明式标记、译文及 CSS 按实际内容说明排除理由与页面验证。无法可靠取得变更范围分支数据时记为未核验，并记录采集缺口。
4. 运行 `inspect-tasks`，保存实际输出、检查范围、T001–T006 逐项状态及全部未完成项编号，与原生清单逐项比对。复核两份清单中的 T005 文件范围、对 `standings-group-isolation` 的依赖、两个键盘用例，以及 T006 的独立预览条件。发现遗漏或状态差异时记录并复查。分别记录通过、失败、跳过及待人工签认。既有人工交接如适用，在对应原生任务中注明负责人、环境、步骤、预期、证据要求和是否发布必需，由授权执行人填写执行日期、实际环境、结果证据并签认。签认前保留待验收。本次计划未新增人工发布门禁。
